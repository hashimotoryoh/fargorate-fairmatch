# ホスティング候補の調査

ゲームのスコアなどを永続化するにあたり、デプロイ先とデータベースの候補を調べた記録である。価格や無料枠は2026年8月時点で確認したものであり、各サービスの都合で変わりうる。実際に契約する前に必ず一次情報を確認すること。

## このアプリの前提

候補を評価するうえで効いてくる、このリポジトリ固有の条件を先に挙げる。

- **SSRが必要**: Nitroのサーバールート（`server/api/`）で外部APIを呼び、認証ミドルウェアもSSR時にリダイレクトとヘッダーを扱う。静的ホスティング（GitHub Pagesなど）だけでは成立しない
- **セッションはDBを要さない**: Nuxt Auth Utils は署名・暗号化したクッキーにセッションを収める。スコアの永続化を入れるまで、サーバー側の状態は無い
- **Nuxt Content が既にDBを要求しうる**: Nuxt Content v3 はビルド時にMarkdownをSQLiteのダンプへ書き出す。サーバーレス環境ではインスタンスが使い捨てられるため、コールドスタートのたびに `/tmp` へ復元される。共有DB（D1・Postgres・libSQL）を `content.database` に指定すればこれを避けられる。**つまりスコア用に用意するDBは、Nuxt Content の置き場所としても使い回せる**
- **書き込み量はごく小さい**: 1試合あたり数行から数十行の規模で、どの候補の無料枠でも桁違いに余る。費用を決めるのはDBの従量課金ではなく、常時稼働する実行環境の側である
- **利用者は日本が中心**: 東京リージョンかエッジで動かせると体感が良い
- **収益化していない個人プロジェクト**: 非商用限定の無料プランも選択肢に入る

## 候補の比較

| 候補                                              | 月額の目安         | データベース             | 位置づけ                                   |
| ------------------------------------------------- | ------------------ | ------------------------ | ------------------------------------------ |
| Cloudflare Workers + D1                           | $5（Workers Paid） | D1（同一ベンダー）       | 本命。SSRの上限とDBが1つの契約で片付く     |
| Vercel Hobby + Turso または Neon                  | $0                 | 別ベンダーの無料枠       | 無料で始める案。非商用限定・上限で停止     |
| Google Cloud Run + Turso または Neon              | $0〜数十円         | 別ベンダーの無料枠       | 東京リージョンでNode.jsをそのまま動かせる  |
| VPS + SQLite                                      | ¥296〜¥650         | ローカルのSQLiteファイル | 制限から解放される代わりに運用の手間を負う |
| Netlify / Render / Railway / Fly.io / Deno Deploy | 条件付き           | 各種                     | 今回は見送り（後述）                       |

## 1. Cloudflare Workers + D1（本命）

静的アセットをWorkersのStatic Assetsで配り、SSRとAPIをWorkerで動かし、スコアをD1に置く構成。

**良い点**

- **DBが同じ契約に含まれる**: D1は無料枠でも5GBのストレージ、1日あたり500万行の読み取り・10万行の書き込みまで使える。このアプリの規模では実質的に上限に当たらない
- **Nuxt Content が D1 を正式に対応している**: `content.database` に `{ type: 'd1', bindingName: ... }` を指定するだけで、Markdownの置き場所も同じD1に寄せられる。追加のベンダーが増えない
- **静的アセットの配信は無料かつ無制限**で、リクエスト数に数えられない
- コールドスタートが実質無く、エッジで動くため日本からの応答も速い

**注意点**

- **無料プランは1リクエストあたりCPU 10msの上限**があり、SSRは10〜20ms程度使うため超えやすい。超えると `Error 1102` で失敗する。公開ページを可能な限りプリレンダしてWorkerを通る経路を減らせば無料枠に収まる余地はあるが、**安定して運用するなら $5/月 の Workers Paid が前提**と考えるのが現実的（Paidは1リクエストあたり既定30秒のCPU時間、月1000万リクエスト込み）
- Workersはエッジランタイムであり、Node.js固有のAPIを使う依存を足したときに互換性で詰まる可能性が残る。現状の依存（`node:sqlite` は Nuxt Content のビルド時利用のみ）では問題にならない見込みだが、将来の依存追加時に効いてくる

## 2. Vercel Hobby + Turso（libSQL）または Neon（Postgres）

Nuxtのデプロイ先として最も摩擦が少なく、**無料で始められる**組み合わせ。

**良い点**

- Nuxtの公式プリセットがあり、GitHub連携で繋ぐだけで動く。`VERCEL_GIT_COMMIT_SHA` は既に `nuxt.config.ts` の `resolveCommitSha()` が読んでいる
- HobbyでもFunctionsのリージョンを1つ選べるため、東京（`hnd1`）を指定できる（複数リージョンへの配置はPro以上）
- DBは無料枠が厚い。Tursoは5GB・月5億行の読み取り・月1000万行の書き込み、Neonは0.5GB・月100 CU時間。Nuxt Content はどちらのアダプター（`libsql` / `postgres`）にも対応する

**注意点**

- **Hobbyは非商用限定**である。収益化する段になったらPro（$20/月）へ移る必要があり、移行コストを最初から織り込んでおくこと
- **上限に達すると超過課金ではなく停止する**（Hobbyにはオーバーレージが無い）。月100GBの転送・100万リクエスト・4 CPU時間などが目安
- Neonはアイドル5分でゼロにスケールするため、低頻度のアクセスだとコールドスタートが乗る。Tursoの方がこの点は素直

## 3. Google Cloud Run + Turso または Neon

コンテナをそのまま東京リージョンで動かす案。

**良い点**

- Node.jsのランタイムをそのまま使えるため、エッジランタイムの互換性を気にしなくてよい
- 常時無料枠が月200万リクエスト・36万GB秒・18万vCPU秒あり、この規模なら実質無料に収まる
- ゼロスケールするためアイドル中の課金が無い

**注意点**

- Dockerfileとデプロイの経路を自前で用意する必要があり、上の2つより手間がかかる
- Artifact Registryのストレージなど、無料枠に含まれない微少な課金が発生しうる
- ゼロスケールからのコールドスタートがある

## 4. VPS + SQLite

1台のVPSでNode.jsを常駐させ、SQLiteのファイルを同じディスクに置く案。

**良い点**

- **費用が読み切れて安い**。ConoHa VPSの512MBプランが月460円（36か月契約なら月296円）、さくらのVPSの512MBプランが月643円。海外で良ければHetznerがさらに安い
- リクエスト数やCPU時間の上限が無く、無料枠の停止に怯えなくてよい
- SQLiteをファイルとして持てるため、Nuxt Content もスコアも素直に同居できる

**注意点**

- **運用を自分で持つことになる**。OSの更新、TLS証明書、プロセスの常駐、デプロイの仕組み、そしてバックアップまで自分で用意する必要がある
- 単一障害点であり、ディスクが飛べばスコアも消える。Litestream などでのバックアップを別途組むこと
- 512MBのメモリでNuxtのビルドを回すのは厳しい。ビルドはGitHub Actionsなど別の場所で行い、成果物だけを置く形にすること

## 5. 見送った候補

- **Netlify**: 2025年9月以降のプランはクレジット制で、無料枠は月300クレジット（転送量にして15GB程度）と細い。使い切ると配信そのものが止まる
- **Render**: 無料のWebサービスは15分のアイドルで停止し、次のリクエストで復帰に1分ほどかかる。加えて**無料のPostgresは作成から30日で失効して削除される**ため、永続化の置き場所にはできない
- **Railway**: 無料枠は初月$5・以降は月$1のクレジットのみで、実質はHobbyの$5/月から。同じ$5ならCloudflareの方が上限に余裕がある
- **Fly.io**: 2024年に恒久無料枠が廃止された。shared-cpu-1x 256MBで月$2前後と安いものの、無料にはならず、運用の手間はVPSに近い
- **Deno Deploy**: 無料枠は月100万リクエスト・CPU 50ms/リクエストと悪くないが、NuxtをDenoランタイムで動かす構成の実績が薄く、詰まったときの情報が少ない
- **Supabase**: DBとして無料枠は使えるが、**7日間アクセスが無いとプロジェクトが自動で一時停止する**。アクセスが途切れがちな時期に止まるリスクを抱えるため、常時稼働が前提の置き場所には向かない

## 費用のまとめ

- **完全に無料**: Vercel Hobby + Turso、または Cloud Run + Turso
- **月$5（およそ¥750〜¥800、為替次第）**: Cloudflare Workers Paid + D1
- **月¥296〜¥650**: VPS + SQLite（ただし運用の手間が上乗せされる）

## 判断の目安

1. **まず無料で始めたいなら Vercel Hobby + Turso**。Nuxtとの相性が良く、DBは Nuxt Content と共用できる。非商用限定である点と、上限超過で停止する点だけ受け入れられるかを見ること
2. **落ち着いた運用を優先するなら Cloudflare Workers Paid + D1**。月$5でSSRのCPU上限もDBも一度に片付き、ベンダーが1つに収まる。無料プランのCPU 10ms上限はSSRには厳しいため、Cloudflareを選ぶならPaid前提で考えること
3. **VPSは、上限や規約から解放されたい場合の選択肢**。費用は最も安い部類だが、その差額は運用の手間として支払うことになる

いずれの候補でも、DBは Nuxt Content とスコアで**1つに寄せる**方針を保つこと。別々のベンダーに分けると、設定と障害の切り分けが二重になるだけで得るものが無い。

## 補足: そもそもDBを持たない選択肢

スコアを端末内（`localStorage` や IndexedDB）に置けば、ホスティングは現状のまま無料の範囲で足りる。ただし次を失う。

- 端末をまたいだ引き継ぎ（スマホで入力した対戦をPCで振り返る、など）
- ブラウザのデータ削除に対する耐性
- 対戦相手と同じ試合を共有する将来の拡張

「対戦中のスコア入力」だけなら端末内で足りるが、「対戦成績の振り返り」を実現するならサーバー側の永続化が要る。どちらを狙うかで必要な投資が変わるため、先に決めておくとよい。

### 永続化しない場合のホスティング

DBを持たないと決めた場合でも、**静的ホスティングにはできない**。サーバールートが要る理由は永続化ではなく次の3つであり、いずれも残るためである。

- FargoRateのAPIをブラウザから直接叩けない（CORSの制約）
- reCAPTCHAのシークレットキーによる検証
- セッションクッキーの署名・暗号化

そのうえで、選ぶ対象は「Nitroが動く場所」だけに絞られる。

- **Vercel Hobby 単体（$0）**: 外部DBが一切不要になる。`@nuxt/content` のvercelプリセットは既定で `{ type: 'sqlite', filename: '/tmp/contents.sqlite' }` を使うため、Markdownはインスタンスの `/tmp` に復元される。コールドスタートの復元コストだけが乗るが、公開ページをプリレンダすればほぼ消える
- **Cloudflare Workers**: **永続化が不要でもD1が要る**。Workersには `/tmp` が無く、cloudflareプリセットは `sqlite` の指定を検出すると警告のうえ `{ type: 'd1', bindingName: 'DB' }` へ強制的に切り替える。Nuxt Content を積んでいる限り「DBなし」の構成にはならないため、DBが要らない状況ではCloudflareを選ぶ動機がむしろ弱くなる
- **Cloud Run（実質$0）**: nodeプリセットでローカルのSQLiteをそのまま使える。手間はDockerfileの分だけ
- **VPS**: 守るべきデータが無いなら、OSの更新やバックアップを自分で背負う見返りが小さい

**データが無いうちは移行コストがほぼゼロである**点が効いてくる。セッションはクッキーに閉じており、サーバー側に守るべき状態が無いため、後から乗り換えても失うものがない。ロックインが生まれるのはDBを持った瞬間なので、永続化を後回しにするなら最も手数の少ない置き場所（Vercel Hobby）に置き、永続化を入れる段で改めて選び直せばよい。

## 補足: 永続化と認証の強さ

このアプリの認証は、名前とFargoRate IDを知っていれば誰にでもなれる仕組みであり、本人性を検証していない（`AGENTS.md` の「認証」を参照）。スコアをメンバーシップIDだけを鍵にして保存すると、**他人の対戦履歴を読んだり上書きしたりできてしまう**。

これはホスティングの選択とは独立した設計上の問題だが、永続化を始める時点で必ず決めておく必要がある。ブラウザごとの秘密の識別子をセッションに持たせて所有者を判定するなど、鍵の設計を先に固めること。
